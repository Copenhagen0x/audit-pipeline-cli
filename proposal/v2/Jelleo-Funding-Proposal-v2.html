02 · Architecture

Four interlocking pillars, eight internal layers

Four interlocking pillars wrap a bug-finding pipeline that runs on every cycle. The pillars are what the engine ships as capabilities: live mainnet detection (P1), cross-protocol propagation (P2), closed-loop fix delivery (P3), tamper-proof attestation (P4). Underneath them, eight internal layers execute the work — most of them inside P3, which contains the bug-finding pipeline itself. No platform today combines all four.

P1

Counterfactual mainnet detection

Always-on watchdog on the deployed surface. Per-transaction parallel simulation; state divergence flags the transaction within seconds of slot finality.

Today: shadow.py runs in two modes — log-pattern detection (regex match against on-chain program logs) and account-state-delta tracking (watches u128 / u64 invariant fields for forbidden transitions). Commit-triggered on the upstream repo. This is the engine's L6 layer.

Funded scope: sub-slot replay for time-sensitive invariants requires validator-grade infrastructure or a premium archival-RPC subscription — that's the real funded dependency. Live mainnet ingestion and on-call alert routing ship as engineering work during the 12 months.

P2

Cross-protocol bug-class propagation

When a bug class is disclosed anywhere, the engine extracts the structural pattern and searches every indexed protocol in the corpus — vulnerable instances flagged in minutes.

Today: propagate.py, propagate_ast.py, and propagate_chain.py drive a structural pattern extractor over a multi-language corpus indexed across all four supported languages. Substring + regex signature search at the source level. Operational across the same four-language adapter stack the rest of the engine uses.

Funded scope: running propagation continuously at full depth across the indexed corpus is API-compute bound — funding pays the compute. AST-level pattern matching and disclosure-feed integrations (Immunefi, GitHub Security Advisory, public PR feed) ship as engineering work during the 12 months.

P3

Closed-loop fix bundle — the core of the engine

Bug + agent-authored fix + Kani proof + tests, bundled as a single PR with five-gate verification before any disclosure ships. The heaviest pillar — it contains the bug-finding pipeline itself, organized as seven internal layers.

Conceptually, P3 runs a four-step methodology — catalog hypotheses → tool-using verification → empirical confirmation → sibling derivation — at production depth, language-aware, with formal-verification synthesis and fix-bundle assembly chained on the end. The seven layers below are how those four steps execute:

  • L1 Recon — multi-agent parallel hypothesis verification. Jelleo dispatches each hypothesis to a tool-using agent with read_file / grep / find_function; the agent renders a line-cited verdict (TRUE / FALSE / INCONCLUSIVE + confidence). Language-aware system prompts per stack. LLM-provider-agnostic abstraction layer (no vendor lock-in at the model).
  • L1.5 Debate — adversarial second-opinion gate on contested or HIGH-severity findings; a second agent disputes the first's verdict and a third arbitrates.
  • L2 PoC author — autonomously generates a language-appropriate test (cargo test for Rust, forge test for Solidity, aptos move test for Move, native C harness for C) and compiles it against the actual code.
  • L2.5 Triage — fast-path regex filter + LLM judge classifies each fire as STRONG / SOFT / FALSE / LOST. Saves $200–500 per cycle in wasted formal-verification dispatch.
  • L3 Formal verification — Kani for Rust, CBMC for C, Move Prover for Aptos, Slither for Solidity. Math-grade proof attempt on STRONG fires; produces a model-checked counterexample if the bug is real.
  • L4 Fuzz coverage expansion — AFL corpora expansion to widen coverage past what the static pipeline reached.
  • L5 Bundle assembly + 5-gate verification — patch + Kani proof + tests + writeup, bundled as a single PR. Five gates: (1) patch authoring via Claude, (2) machine verification (compilation, test fires, Kani re-runs), (3) operator review, (4) typed-authorization phrase, (5) tuple-matching recheck of (finding, engine SHA, patch SHA) before PR open. No PR opens without all five.

Today: P3 is COMPLETE across all four languages (Rust/Anchor, Move, Solidity, C). Code lives in bundle/ (assembly, patcher, verifier, auth) plus per-layer modules in commands/ (recon, debate, poc, triage, synth_kani, expand_coverage, bundle).

Funded scope: the engine runs at single-pass exploratory depth today to stay within self-funded budget. Funded operation runs at full multi-round depth — refinement on every hypothesis, formal-verification synthesis on every Critical/High, attack-chain enumeration — at substantially higher per-cycle API compute. That compute is the real funded dependency. Native GitHub PR integration (the engine drafts PRs today but a human opens them by design) and general-case fix-bundle templates ship as engineering work during the 12 months.

P4

Tamper-proof attestation registry

Every cycle publishes a signed Merkle root — which invariants were verified at which commit SHA — cryptographically signed so anyone can independently verify a cycle's findings without trusting Jelleo.

Today (off-chain): merkle.py computes a per-cycle Merkle root over the findings set; Ed25519 signing seeded from HKDF over the platform private key; per-cycle merkle.json sidecars published to the public cycle archive at jelleo.com/cycles/; hourly heartbeat publishes the engine's current root + uptime. This is the engine's 8th internal layer — outside the per-cycle bug-finding pipeline (L1–L5) and the always-on mainnet shadow (L6), but executed every cycle as the trust-anchor step.

Funded scope (Y1): a third-party audit covering the trust chain before P4 mainnet ship — $80K minimum engagement at top Solana audit firms, scoped against the standard ~$14/LOC rate to cover approximately 5,500 LOC: the ~500-LOC Anchor program PLUS the security-critical engine paths that produce and sign attestations (Merkle root computation, Ed25519 signing path, cycle attestation lifecycle, per-customer scoping, key derivation). Required because we cannot credibly self-audit our own trust-anchor code; without it the chain breaks. The Anchor program itself, on-chain Merkle publication, indexer + query API all ship as engineering work during the 12 months. Devnet deployment is free; mainnet ships after the audit clears at day 180.

Y2+ commitment: a full audit of the engine — 58K LOC today across the auditable engine source (~285K LOC across the full project including tests, deploy scripts, website, and docs) — is a Year-2-and-beyond commitment as revenue can absorb it. The engine grows continuously, so the actual cost of a full-engine audit at the time we commission it will be substantially higher than the ~$812K estimate against today's footprint (58K × $14/LOC). Year-1 audit scope covers the critical trust chain that produces and signs attestations; the broader pipeline, LLM-dispatch, and reporting code is open-source under Apache-2.0 and relies on public scrutiny in the interim.

03 · Learning loop

What compounds with every cycle

Jelleo improves cycle-over-cycle — every confirmed finding adds to the catalog, every propagation run extends reach, every false-positive judgment is captured. The compounding is what continuous coverage actually delivers.

What actually compounds

01

Language-portable methodology

The same 4-step pipeline (catalog → verify → confirm → derive) runs on each of the four supported language stacks. Pattern detection is language-aware per stack — Rust/Anchor, Move, Solidity, and C each get their own bug catalog and tooling references. Adding a new language ships an adapter, not a rewrite; the per-language catalog then grows as confirmations accumulate in that stack. Methodology portability is what made covering four languages with a solo team possible in the first place.

02

Sibling derivation in practice

Every confirmed bug auto-generates 3–5 sibling hypotheses targeting the same class through different code paths. Confirmed siblings can spawn their own siblings. The catalog deepens recursively with every cycle. The engine's first disclosure (F7 — see appendix) spawned 6 siblings; cross-protocol propagation then swept the indexed corpus (Drift, Mango, Jupiter — 517 files) for the same structural pattern.

03

Engine learns from external disclosures

Disclosure-feed ingestion (Immunefi, GitHub Security Advisory, public PR feed — ships as engineering work during the funded 12 months) means every bug class disclosed anywhere in the ecosystem becomes a propagation target. The engine does not need to find a bug first to know what to search for — external catalog growth automatically extends coverage across the indexed corpus.

Continuous vs point-in-time, over a 12-month horizon

Point-in-time firm engagement

  • Comprehensive engagement spanning ~2 months for Solana-scale programs, plus post-delivery touch-ups
  • Coverage closes at engagement end; subsequent commits await next engagement
  • Findings reflect the codebase scope at delivery
  • Each engagement scoped fresh per protocol
  • External disclosures land outside the engagement window

Jelleo continuous coverage

  • Every commit re-audited; signed receipt published
  • Per-language catalog grows with every confirmed finding
  • Sibling derivation deepens variant pattern coverage cycle-over-cycle
  • Cross-protocol propagation extends reach across the indexed corpus
  • Disclosure feeds keep the catalog current with the ecosystem (funded delta)
